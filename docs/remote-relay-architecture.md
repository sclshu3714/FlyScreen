# 玄鸟内置中继 / NAT 穿透：实现方案

| 项 | 内容 |
|----|------|
| 性质 | 架构与实现方案分析，不含代码改动 |
| 日期 | 2026-11-11 |
| 前提 | 家里电脑与公司电脑都没有公网 IP；不使用 Tailscale/ZeroTier 等第三方；用户只装玄鸟；公司网络可能只允许出站 443；IPv6 未知 |
| 结论 | **可实现**。唯一自洽路径是“玄鸟自建信令 + STUN + 中继（TURN 类）”，客户端出站连接，中继只转发密文；不要求用户装第二个软件、不改路由器、不开入站端口 |

---

## 0. 先接受一个硬约束

两个都在 NAT 后面的设备，彼此**无法主动入站**。它们只能主动连一个公网地址。因此，要“双方都不装第三方、都没有公网 IP”还能互通，只有三种可能：

1. **玄鸟自己的公网中继服务器**（本方案）；
2. 家里或公司其中一方有公网 IP / 可用 IPv6；
3. 装第三方 overlay（你已否决）。

**如果没有 1、2、3，数学上无解。** 这不是实现技巧问题，是网络拓扑决定的。

所以本方案的核心不是“要不要中继”，而是：

- 中继服务器由**玄鸟自己部署**，用户不感知、不装第二个软件；
- 先尝试 **IPv6 / P2P 打洞直连**，失败才走中继，尽量少用中继；
- 中继只转发**端到端加密后的密文**，看不到内容；
- 客户端只做出站连接（443/TLS 或 QUIC），不改路由器、不开入站端口、不要管理员权限（安装除外）。

## 1. 总体架构

```text
        公司电脑 A（NAT 后）                 家里电脑 C（NAT/CGNAT 后）
             │                                      │
             │  出站 TLS/QUIC 443                   │  出站 TLS/QUIC 443
             └──────────────┬───────────────────────┘
                            ▼
              ┌────────────────────────────────┐
              │  玄鸟接入服务器（公网 VPS）        │
              │  1. 信令 / 配对 / 设备认证         │
              │  2. STUN（发现公网映射）           │
              │  3. 中继（TURN 类，转发密文）      │
              └────────────────────────────────┘

直连优先：A ←── IPv6 直连 / UDP 打洞 ──→ C
中继兜底：A ←── 加密 UDP/TCP ──→ 中继 ←── 加密 UDP/TCP ──→ C
```

三个角色：

| 角色 | 作用 | 是否必须 |
|------|------|----------|
| 信令服务 | 设备注册、配对码校验、交换候选地址、下发中继凭证 | 必须 |
| STUN | 告诉客户端“你在公网看到的地址:端口”，用于打洞 | 必须（可和中继同机） |
| 中继 | 直连失败时转发加密数据 | 必须（无公网 IP 时的兜底） |

**不是必须**：账号体系、云盘、第三方 SDK。设备用密钥对 + 配对码即可，不强制注册账号。

## 2. 连接建立流程

### 2.1 配对

1. 家里电脑 C 打开“远程设备”，显示 6 位配对码（5 分钟有效，限次）。
2. 公司电脑 A 输入配对码；两端各自生成/复用设备密钥对。
3. 信令服务器校验配对码，把 A、C 绑定到同一会话，交换公钥指纹。
4. 双方确认设备名/形态（Desktop），完成信任。

> 配对码只用于首次绑定；之后靠设备密钥重连，不需要再输码。也不需要账号。

### 2.2 候选地址收集

两端各自收集：

- **host**：本机所有网卡地址（含公司内网、家里内网）；
- **srflx**：通过 STUN 得到的公网映射地址；
- **IPv6**：本机全局 IPv6 地址（如果有）；
- **relay**：向中继申请一个转发端口/会话。

### 2.3 直连尝试（优先，省中继带宽）

按顺序尝试：

1. **IPv6 直连**：双方都有全局 IPv6 且防火墙允许 → 直接连，延迟最低。
2. **UDP 打洞**：双方用 STUN 得到的公网地址互发穿透包；锥形 NAT 成功率高，对称 NAT/CGNAT 容易失败。
3. **UPnP/NAT-PMP/PCP**：尝试让家里路由器自动映射端口；不保证成功，不作为主路径。
4. **失败判定**：3–5 秒内没有建立双向连通 → 转中继。

### 2.4 中继兜底

1. 信令服务器为中继会话分配一个 relay 端点（例如 `relay.example.com:443`）。
2. A、C 各自主动连中继（TLS/QUIC 443），中继按 session id 把两端数据互转。
3. 中继只看到密文；会话密钥由 A、C 通过 Noise/ECDH 协商，中继无解密能力。
4. 断线后自动重连；中继 session 保留一段时间，避免重新配对。

### 2.5 传输承载

- **控制面**：TLS/WebSocket 443 或 QUIC，承载配对、候选交换、心跳、键鼠/布局/投影信令。
- **数据面**：优先 QUIC/UDP（投影帧、文件、剪贴板）；受限网络回退 TCP 443。
- 现有 `ConnectionManager` 的控制通道 + Bulk 通道可以整体跑在这条传输上；不必改消息语义。

## 3. 与现有协议怎么接

现有代码是“TCP 15155 直连 + Bulk 第二条 TCP 连接”。接中继有两种做法：

### 方案 A：本地 TCP 代理（MVP，改动最小）

- 玄鸟在本机起一个本地监听（如 `127.0.0.1:15157`），把连接透明转发到远端 peer 的 15155。
- `ConnectionManager` 把“远端地址”指向 `127.0.0.1:15157`，其余协议、投影、文件、剪贴板全部不变。
- 优点：不动消息层，1–2 周可验证。
- 缺点：TCP over TCP 有队头阻塞；投影帧率/延迟不如 UDP；只适合 MVP。

### 方案 B：`IPeerTransport` 抽象（产品化，推荐）

- 在 `ConnectionManager` 和 socket 之间加一层 `IPeerTransport`：
  - `TcpTransport`：现有局域网直连；
  - `RelayTransport`：QUIC/UDP 经中继；
  - `DirectTransport`：IPv6/打洞直连。
- `ConnectionManager` 只依赖 `IPeerTransport` 的 `Stream`/`Datagram` 接口，不关心底层是 LAN 还是中继。
- 优点：投影帧可以走 UDP/QUIC，不被 TCP 队头阻塞；直连/中继可无缝切换。
- 成本：2–3 周重构 + 回归；但这是长期正确的做法。

**建议**：先用方案 A 验证场景，再在 v1.1.1 换方案 B。

## 4. 投影怎么优化

中继本身只多一跳，真正“慢”通常来自：

- 中继跨地域/跨运营商；
- TCP 队头阻塞，丢一个包卡住整帧；
- 带宽不足，JPEG 1080p 12fps 需要 10–30Mbps；
- 没有自适应，网络抖动时花屏/卡顿。

对应措施：

| 问题 | 措施 |
|------|------|
| 中继远 | 多地域中继，按 RTT 选自最近节点；同城 10–30ms，跨省 30–80ms |
| 队头阻塞 | 投影帧走 QUIC/UDP，迟到帧直接丢，不阻塞后续帧 |
| 带宽不够 | 自适应分辨率/帧率；720p/10fps 约 3–5Mbps；H.264/E2 进一步降码率 |
| 丢包 | FEC/前向纠错 + 关键帧重传；不追求每帧完整 |
| 声音 | PCM 换 Opus；抖动缓冲；跨公网语音可用，音乐不保证 |
| 远程回控 | 输入事件走可靠控制通道；延迟 50–150ms，点击/打字可用，高频操作不保证 |

**产品口径**：跨公网投影定位为“看文档/代码/桌面状态”，不承诺视频/游戏级流畅；要低延迟，优先 IPv6/打洞直连，中继只是兜底。

## 5. 安全

| 项 | 做法 |
|----|------|
| 设备身份 | 每台设备生成 X25519 密钥对；公钥指纹随配对码确认 |
| 配对 | 6 位码 + 5 分钟有效 + 限次；防暴力 |
| 端到端加密 | Noise IK / ECDH + ChaCha20-Poly1305；中继只转发密文 |
| 中继凭证 | 短时 token，绑定设备/会话；限速、防滥用 |
| 入站端口 | 不需要；两端只做出站 443/QUIC |
| 隐私 | 中继不存储内容；只保留最小连接元数据 |
| 公司 policy | 只做出站 443；不绕过公司防火墙；不承诺“任何公司网络都能用” |

## 6. 服务器部署与成本

中继是唯一持续性成本。可选：

| 方式 | 说明 | 成本 |
|------|------|------|
| 自建小 VPS | 2C2G、5–10Mbps，部署信令+STUN+中继，Docker 一键 | 约 ¥50–200/月（视地域/带宽） |
| 多地域 | 同城/华东/华南各一台，按 RTT 选 | 成本×N |
| 自托管 | 用户自己有公网 VPS/NAS，跑玄鸟 relay 二进制 | 用户自付 |
| 免费/低成本云 | 部分云免费 tier，但带宽/稳定性不保证 | 不适合正式产品 |

**流量估算**（单路投影）：

- 720p/10fps、3–5Mbps：1 小时约 1.3–2.2GB；
- 1080p/12fps、10–30Mbps：1 小时约 4.5–13.5GB；
- 若每天 1 小时、每月 22 天：720p 约 30–50GB；1080p 约 100–300GB。

**建议**：MVP 先 720p/10fps + 自适应，优先直连，减少中继流量；后续按需求开 1080p。

> 如果完全不想承担任何服务器成本，也不接受 IPv6/公网 IP，也不装第三方，那么该场景没有可行解。这是必须提前说清的边界。

### 6.1 用绿联 NAS + Docker 做中继节点（可行，但看清边界）

附件 1：UGREEN NAS Docker 里 `macos` 容器映射 `8006:8006`、`5900:5900`，说明容器端口可以在 NAS 上映射；旁边还有一个 `tailscale` 容器在跑。
附件 2：`https://app-8006-sclshu.cn65.ugdocker.link` 能在远端打开 macOS 的 noVNC 页面。

要区分三件事：

| 方式 | 实际是什么 | 能不能跨公网 |
|------|------------|--------------|
| Docker `-p 8443:8443` | 只把容器端口映射到 NAS 的局域网 IP | **不能**，公司/外面访问不到家里 NAS 的私网 IP |
| 路由器端口映射 / 公网 IP/IPv6 | 把 NAS 暴露到公网 | 能，但家里多为 CGNAT，且要开入站 |
| `*.ugdocker.link` | 绿联云的**远程访问反代/中继**，不是公网 IP | 能，但依赖绿联云，且主要是 HTTP/HTTPS |

`app-8006...` 能打开 noVNC，说明绿联 Link 至少能代理 **HTTPS + WebSocket**（noVNC 就是 WebSocket）。这对“玄鸟 relay”是个好消息：把 relay 做成 **WSS（WebSocket over TLS）** 服务，映射到 NAS 的一个端口（如 8443），再用绿联 Link 生成 `https://app-8443-....ugdocker.link`，公司端和家里端都主动连这个 WSS 地址，就能由 NAS 转发。

**能做什么：**

- 信令/配对：设备注册、6 位配对码、交换会话信息。
- 中继：两端连 WSS，NAS 容器按 session 转发二进制帧；端到端加密，NAS 只转密文。
- 自托管：Docker 镜像 + compose，用户自己的 NAS 就能跑；不装第二个客户端软件。
- 附件里的 `tailscale` 容器与本方案无关；按你的要求不使用它，本方案不依赖它。

**不能做什么：**

- 不能靠 Docker 端口映射本身让公司访问到家里 NAS；公网可达性来自绿联 Link 或公网 IP/IPv6。
- 不能保证 P2P 直连：绿联 Link 主要是 HTTPS/WSS，不提供 UDP/任意 TCP；没有公网 IP/IPv6 时，实际模式是**中继**，不是 P2P。
- 不能承诺低延迟：路径是 公司 → 绿联云 → 家里 NAS → 家里电脑，多一跳；noVNC 能开，不代表 1080p 投影能流畅。
- 仍是第三方依赖：绿联云是第三方。要“完全不依赖第三方”，只能公网 IP/IPv6 或自建 VPS。

**建议的验证顺序：**

1. 在 NAS Docker 起一个最小 WSS echo/relay 容器，映射 `8443:8443`，用绿联 Link 生成 `app-8443-...` 地址。
2. 公司电脑用 `wss://app-8443-.../relay` 连上，家里电脑也用同一地址连上；测 1MB/10MB 往返、延迟、长连接 10 分钟是否断。
3. 能稳定跑，再把 FlyScreen 的投影帧灌进去，测 720p/10fps；能接受再产品化。
4. 如果绿联 Link 限速/断长连接，退回 VPS 中继；NAS 方案只作为“自托管/个人用”选项。

**成本**：NAS 已有，Docker 容器本身几乎不占资源（macos 容器占 7.9GB，relay 容器通常 <200MB）；主要成本是家里上行带宽和绿联 Link 的限额。若绿联 Link 免费额度不够，仍要 VPS 或付费。

### 6.2 产品化部署模型：自托管中继 + 第三方 overlay（无官方中继）

你已拍板：玄鸟是开源项目，**不提供官方中继服务器**，只提供能力。因此没有“官方中继”这个角色，只有三种用户自带网络（BYO）的方式：

| 模式 | 用户要做什么 | 谁承担服务器/带宽 | 适合谁 | 代价 |
|------|--------------|------------------|--------|------|
| **自托管中继**（主路径） | 部署玄鸟 relay 到 NAS/VPS；填 relay 地址 + 配对码 | 用户自己 | 有 NAS/VPS、愿意动手的用户 | 门槛高；需要公网可达（公网 IP/IPv6/UGREEN Link/frp 等） |
| **第三方 overlay**（备选） | 两端装 Tailscale/ZeroTier；填虚拟 IP | 第三方 | 已用 overlay、公司允许的用户 | 多装一个软件；公司 policy；你个人不接受但可作为用户选项 |
| **直连地址** | 公网 IP/IPv6 + 端口；填 IP:端口 | 用户自己的网络 | 少数有公网地址的用户 | 不通用；公司/家庭多 NAT |

**没有“官方中继”**：玄鸟不运营服务器、不承担带宽、不做账号/付费/配额；所有远程流量都由用户自己的 relay 或 overlay 承载。

**自托管中继服务的定位：**

- 一个独立、可 Docker 部署的服务，包含信令 + STUN + 中继；
- 用户部署到公网 VPS，或部署到 NAS（NAS 需有公网可达路径：公网 IP/IPv6、UGREEN Link、frp 等）；
- 用户自己用，也可以分享给朋友/团队自己部署；玄鸟不提供托管实例；
- 客户端只填 `relay URL + 配对码`，不要求用户装第二个客户端软件（relay 是服务端，不是客户端）。

**第三方 overlay 的定位：**

- 不打包、不代装、不作为默认；
- 玄鸟只提供“手动远端地址/指定网卡”接入：用户填 overlay 虚拟 IP:15155；
- 文档写清 Tailscale/ZeroTier 两种示例；公司 policy 由用户自己判断；
- 这条路径不需要 relay 服务，适合已有 overlay 的用户。

**共同的产品语义：**

- 远程设备 = 布局第 4 槽 + “远程”标记；
- 默认不参与边缘穿边（跨公网延迟高）；
- 可作为投影目标；需要操作时单独“远程控制”；
- 断线重连、延迟/带宽提示、连接方式（自建中继/overlay/直连）可见。

**边界：**

- 不承诺“任何网络都能用”：公司封 443、对称 NAT、NAS 无公网路径时，用户需要自己解决可达性；
- 不自建官方中继，所以没有统一 SLA、没有统一域名/证书、没有配额系统；
- 安全由用户自己的 relay 负责：TLS、设备密钥、E2E 加密、限流；玄鸟提供默认安全配置和文档，但不托管。

## 7. 分期实现

### v1.1.0 远程接入 MVP（6–8 周）

- 交付独立 relay 服务（Docker 镜像 + compose）：信令 + STUN + WSS/TCP 443 中继；用户部署到 VPS 或 NAS。
- 客户端“远程设备”入口：
  - 自建中继：填 relay URL + 配对码；
  - 第三方 overlay：填虚拟 IP:15155（Tailscale/ZeroTier 示例见文档）。
- `IPeerTransport` 抽象（LAN / relay / 手动地址）；MVP 可先用本地 TCP 代理。
- 远程槽位（“远程”标记，不参与边缘穿边）。
- 投影：家里 C → 指定公司 A，720p/10fps，首帧 <5s。
- 文档：VPS Docker、NAS Docker、Tailscale/ZeroTier 三种接入示例；公网可达性说明。
- 验收：用户自建 relay 后，公司只允许出站 443 时能连上并出画面；overlay 路径能手动接入；断线自动重连。

### v1.1.1 直连优先 + 传输抽象（3–4 周）

- IPv6 候选 + UDP 打洞；成功则直连，失败才走用户自建 relay。
- `IPeerTransport` 抽象，替换本地代理。
- 延迟/带宽指示；直连/中继状态可见。
- 验收：同城直连 RTT <20ms；打洞失败 5 秒内切用户自建 relay，不长时间卡住。

### v1.1.2 投影传输优化（4–6 周）

- QUIC/UDP 数据面；丢帧不阻塞；FEC。
- 自适应分辨率/帧率；H.264/E2（可选）。
- 声音 Opus；远程回控可选。
- 验收：10Mbps 下 720p 稳定；20Mbps 下 1080p 文档可读；弱网自动降级。

### v1.1.3 自托管运维与平台兼容（持续）

- relay 的多实例/就近选择由用户自己部署；玄鸟提供配置、健康检查、故障切换示例。
- 限流/监控/日志模板；安全加固文档；不提供官方配额系统。
- 兼容 UGREEN/Synology/QNAP/Unraid 等 NAS 的 Docker 部署；VPS 一键 compose。
- 验收：用户按文档能在 NAS/VPS 起 relay；单节点故障有明确提示；不承诺官方 SLA。

**总量**：MVP 6–8 周；到“直连优先 + 投影优化”约 13–18 周。

## 8. 布局语义与设备数量

- 2 台公司电脑 + 手机/平板 + 家里电脑 = 4 台，符合现有上限。
- 家里电脑作为**远程槽位**：
  - 出现在设备列表/布局中，带“远程”标记；
  - **默认不参与边缘穿边**（跨公网延迟高，穿边体验差）；
  - 可作为投影目标；需要操作时单独“远程控制”，显示延迟。
- **重要**：现有布局同步是 peer-to-peer，不是中心拓扑。家里电脑只连公司电脑 A 时，它只出现在 A 的布局里；公司电脑 B 看不到它。如果要 B 也看到，需要：
  - C 分别与 A、B 建立两条远程会话（各自一条中继/直连），或
  - 新增“网关共享布局”（A 把 C 的槽位同步给 B），这是额外能力，MVP 不做。
- 建议 MVP 只做“C ↔ 指定 A”，满足“投到指定一台”；B 是否也要看到，作为 v1.1.1 的选项。

## 9. 风险与边界

| 风险 | 说明 | 对策 |
|------|------|------|
| 公司网络禁止出站 | 只允许 80/443 或代理 | 只做 443/TLS；QUIC 失败回退 TCP 443；不保证所有公司 |
| 对称 NAT/CGNAT | 打洞失败率高 | 中继兜底；不承诺“一定直连” |
| 中继带宽成本 | 1080p 流量大 | 720p/自适应；直连优先；用户自己的 relay 做限流 |
| 中继延迟 | 跨地域/跨运营商 | 用户可多实例就近部署；不承诺游戏级 |
| 安全 | 公网暴露风险 | 端到端加密；只出站；短时 token；中继不解密 |
| 合规 | 国内公网服务可能涉及备案 | 上线前确认；自托管模式作为备选 |
| 4 台上限 | 3 公司电脑 + 手机 + 家里 = 5 | 先按 4 台；5 台需改协议 |
| 平台 | 家里可能是 Mac/Linux | Windows 先行；Mac/Linux 按采集能力降级 |

### 9.1 现场核查（公司电脑，2026-11-11）

`ipconfig` 以太网输出：

- Link-local IPv6 Address：`fe80::5e05:4243:aabf:b18d%9`
- IPv4 Address：`10.10.1.15` / `255.255.254.0`
- Default Gateway：`10.10.0.1`

`Get-NetIPAddress -AddressFamily IPv6`：以太网只有 `fe80::/64`（`PrefixOrigin=WellKnown`、`SuffixOrigin=Link`），**没有全局 IPv6**；`Get-NetRoute -AddressFamily IPv6` **没有 `::/0` 默认路由**。

结论：

- `fe80::` 是链路本地地址，只在同一二层网段有效，不能从家里访问；`%9` 是本机接口索引，不是公网地址的一部分。
- `10.10.1.15` 是 RFC1918 私有地址，公司 NAT 后面，家里无法直接访问。
- 该以太网没有全局 IPv6，也没有 IPv6 默认路由；IPv6 直连不能作为本场景的基线。
- 因此本场景必须中继兜底；IPv6 直连只作为“双方都有全局 IPv6 且允许入站”的可选优化。

### 9.2 家里侧出口地址（待确认）

家里侧执行 `Invoke-WebRequest https://api6.ipify.org -UseBasicParsing` 返回 `2a03:90c0:2a1::3fb`。这是 `2000::/3` 范围内的全局 IPv6，不是 `fe80::` 链路本地地址，说明该出口路径具备公网 IPv6。

但仍需确认：

- 这个地址是**家里电脑网卡自身的地址**，还是路由器/代理/VPN 的出口地址；需在家里电脑上跑 `ipconfig` 或 `Get-NetIPAddress -AddressFamily IPv6`，看活动网卡是否有 `2a03:90c0:...` 地址。
- 家里路由器 IPv6 防火墙是否允许**入站**到 TCP 15155（UDP 15156，如走 UDP）。
- 地址是否稳定（前缀是否会随拨号/重启变化）。
- **即使家里有全局 IPv6，公司这台没有全局 IPv6、也没有 `::/0` 默认路由**，公司侧无法发起 IPv6 连接；两端都具备才能直连。

结论不变：本场景以中继为基线；IPv6 直连只在“两端都有全局 IPv6 + 允许入站 + 地址稳定”时作为优化。

### 9.3 公司侧 IPv6 复核（2026-11-11）

公司电脑执行 `Get-NetIPAddress -AddressFamily IPv6` 的结果：

- 所有物理网卡（以太网、WLAN、以太网 3、蓝牙等）只有 `fe80::/64` 链路本地地址；
- `Tailscale` 为 `fd7a:115c:a1e0::3b01:510/128`（ULA，唯一本地地址，不是公网）；
- `Loopback` 为 `::1`；
- **没有任何 `2000::/3` 全局地址**。

`api6.ipify.org` 返回的 `2a03:90c0:2a1::3fb` **不在任何网卡上**，是 Tailscale/VPN 出口节点看到的地址，不是公司电脑的 LAN 地址。

结论：

- 公司侧不具备 IPv6 直连条件；`2a03` 不能作为公司电脑的直连地址。
- 即使家里电脑有全局 IPv6，公司侧没有全局 IPv6/默认路由，两端仍不能 IPv6 直连。
- IPv6 直连在本场景不可行；中继是基线。

## 10. 需要你拍板

1. **主路径选哪个？** 自托管 relay（NAS/VPS）还是第三方 overlay（Tailscale/ZeroTier）？两者都要支持，但 MVP 的文档、验收和默认入口要定主次。
2. **你愿意自己部署 relay 到公网 VPS 吗？** 如果只部署在 NAS，NAS 必须有公网可达路径（公网 IP/IPv6/UGREEN Link/frp），否则公司访问不到。
3. **公司网络是否只允许出站 443？** 如果是，方案按 TLS/443 优先，QUIC 作为可选。
4. **MVP 画质接受 720p/10fps 吗？** 1080p/12fps 会明显吃用户自己的 relay 带宽。
5. **“加入布局”是只让指定的 A 看到，还是 A、B 两台都要看到？** 后者需要两条远程会话或网关共享布局。
6. **家里电脑是 Windows 吗？** Windows 先行最稳；Mac/Linux 的 Host 采集按现有矩阵降级。
