# 需求验证备忘：v1.1 三项新功能是否是真需求

| 项 | 内容 |
|----|------|
| 性质 | 产品需求验证，不改代码 |
| 日期 | 2026-11-11 |
| 方法 | 维护者自身使用 + 同类产品用户公开讨论 + 厂商官方文档 |
| 结论 | 三项都有场景，但强度差三档：**C > A > B**；A 的痛点定义错位，B 的证据被高估 |

> **第三轮评审（2026-11-11）：** 本文 C>A>B 是第二轮结论。用户随后对 C 的搜索效率/卡顿、A 的实际价值提出质疑，C/A 均不再作为 v1.1 的既定范围；最新结论见 [`product-next-version.md`](product-next-version.md) §11。另：Star/Issue 不构成 pre-launch 需求证据，§1.1 已修正。

## 0. 第二轮结论（现已被第三轮评审推翻）

> 以下为第二轮结论，保留作决策轨迹。C/A 已在第三轮被撤下，最新范围见 [`product-next-version.md`](product-next-version.md) §11。

- **C 全设备文件搜索**：三者中最扎实的真需求。替代方案（SMB 映射、逐台 Everything、NAS 索引）门槛明显，FlyScreen 的“已配对设备 + 零配置 + 命中即拉取”有差异化。**保留 P0，作为 v1.1 主功能。**
- **A 配对入网**：真需求，但属于“一次性、增长型”，不是高频使用功能。上一版把痛点归为“输密钥”是错位的；真正痛点是**发现不到、跨网段、防火墙、管理员权限、信任残留**。**保留 P0，但改定义为“零配置连接向导”，预算压到 2 周。**
- **B 跨设备通知**：需求真实且高频，但替代方案强（Phone Link、华为/小米生态）、系统硬约束（Android 15 屏蔽验证码类敏感通知）、隐私成本高，差异化只剩“跨品牌混合生态 + 本地无云”。对一个 pre-launch、单人维护的项目，4 周投入回报不确定。**降为 P1，先做 2 周验证，不进 v1.1。**

**收敛后的 v1.1：C（3 周）+ A（2 周）+ 1 周回归 = 6 周**，比原方案少 2 周，也少一个高风险系统服务。

## 1. 证据基础与局限（先说清楚）

### 1.1 项目处于 pre-launch，不能用 Star/Issue 当需求证据

项目刚上传两天，公开数据为 2 star、0 fork、0 issue。这个数字只能说明**还没有外部用户样本**，不能证明需求不存在，也不能证明需求存在。把它当作“需求否证”是错的。

pre-launch 阶段，需求证据按以下顺序取：

1. **维护者自己的重复痛点**：最近两周有没有真的被这件事挡住？多久一次？现在怎么绕？绕的成本多大？
2. **同类产品用户的公开原话**：能证明“品类有需求”，不能证明“FlyScreen 该做”；
3. **外部用户反馈**：现在没有，等有分发之后再收集。

因此本文的判断是**基于“维护者自身使用 + 同类产品行为”的需求假设**，不是已证实结论；上线前仍要做第 6 节的验证，但验证的第一样本是维护者自己，不是陌生人。

### 1.2 外部证据能证明“品类有需求”，不能证明“FlyScreen 该做”

| 证据 | 说明 | 能证明什么 |
|------|------|------------|
| V2EX 多机键鼠长帖（2025，48 回复） | 用户为“台式机 + 笔记本一套键鼠”试遍 Flow、MWB、Synergy、Deskflow、KVM、对拷线；抱怨跨网段、hosts、键盘切不过去 | 品类需求强；**连接可靠性/可达性是最大痛点**，不是输密钥 |
| V2EX “Windows 共享文件夹太玄学”（2024，4981 浏览 / 29 回复） | 同一局域网里一台电脑死活访问不了共享，防火墙、SMB 签名、来宾登录各种坑 | 跨机找文件/共享的替代方案门槛很高 |
| V2EX “NAS Find”（2026-09，1183 浏览） | 作者因“Mac 上搜 NAS 是灾难”而自建索引服务 | 多系统 + 多存储的搜索需求真实存在 |
| V2EX “Win 顺”（2026-10） | 把“NAS、别的电脑上的共享文件夹也能一起搜”作为头条卖点 | 跨设备搜索是搜索工具的差异化卖点 |
| 华为官方通知同步说明 | 只同步短信、微信、QQ、Welink、钉钉、未接来电；其他应用不支持 | 生态内通知同步也受应用白名单限制 |
| 微软 Phone Link 通知排查 | Android 15 起，第三方无法显示被系统标记为“敏感”的通知，包含 2FA 验证码、一次性密码 | **通知里最高频的“验证码”场景，第三方做不了** |
| 小米 HyperConnect | 已支持通知同步、点击回复，甚至 iPhone ↔ 小米；Mac/iPad 屏幕扩展 | 通知同步是成熟能力，竞争充分 |

**推论：** 品类需求不等于产品机会。C 的替代成本最高、差异化最清楚；B 的替代品最强、限制最硬；A 是转化问题，不是使用问题。

## 2. 判定标准

对每个功能问四个问题，再加一个证据强度：

| 维度 | 含义 |
|------|------|
| 触发频率 | 用户多久遇到一次？每天 / 每周 / 一次性 |
| 替代方案成本 | 现在怎么做？几步？会不会失败？ |
| 愿付代价 | 愿不愿意装第二个 App、开系统权限、改习惯 |
| 不做的损失 | 不做会不会明显影响留存/采用 |
| 证据强度 | 有多少真实用户原话/行为，而非产品经理推断 |

## 3. 逐项分析

### 3.1 A｜配对入网 2.0

#### 场景清单

| # | 场景 | 谁 | 现在怎么做 | 痛点强度 |
|---|------|----|------------|----------|
| A1 | 新买笔记本，第一次加入 4 台设备 | 多机用户 | 装完 → 复制安全密钥 → 到旧机粘贴 → 手动添加名称/IP → 防火墙弹窗 → 摆布局 → 可能单向连接 | 中（一次性，但完不成就是 0） |
| A2 | 公司电脑 + 家里电脑，跨 VLAN/网段 | 办公 + 家用双机 | 加 hosts、手动 IP、关防火墙、换网卡；仍可能发现不到 | 高（直接失败） |
| A3 | 手机首次装 APK | 手机当触控板/被控 | 输密钥 + 开无障碍 + 添加电脑 + 授权 | 高 |
| A4 | 换机/设备丢失，旧 peer 残留 | 老用户 | 不知道在哪移除，或改密钥导致全部重连 | 中 |
| A5 | 临时借用同事电脑 | 办公 | 给长期密钥，事后又不好意思改 | 中 |

#### 证据

- FlyScreen 自身要求：各机填写**相同安全密钥**、Win/Maui-Win **须管理员**、确认局域网发现能看到对方。
- V2EX 2025 帖：罗技 Flow 因“IP 前三段不一致”失败；PowerToys 无界鼠标“要记得添加 hosts”；有人最后退回 KVM/对拷线。说明**用户真正的卡点是网络可达性**，不是“密钥太长”。
- Mouse without Borders 的标准流程就是“一边生成 key，另一边连接”，用户普遍能接受；它被抱怨的是不稳定、键盘切不过去。

#### 判定

**真需求，但属于“增长型/一次性”，不是“高频使用型”。** 上一版把它叫“配对入网 2.0”、主打“不用抄密钥”，只覆盖了 A1 的一小段，没解决 A2/A3 的主要失败点。

#### 修正

改名为 **“零配置连接向导”**，范围：

1. 配对码 / 二维码（二维码内含 IP + 端口，解决“发现不到”）；
2. 手动地址兜底（输入 IP:端口），跨网段/多网卡时可用；
3. 连接前诊断：防火墙规则、网卡选择、端口占用、单向连接原因，给可执行修复；
4. 信任中心：已配对设备、最后在线、移除/拉黑；
5. 临时访客（可选，v1.1.1）；
6. 明确提示“需要管理员权限”，并在安装器/首启文案里提前说明。

**预算从 1.5–2 人周压到 2 人周以内，但验收指标改为“首次连接成功率”，不是“配对码使用率”。**

### 3.2 B｜跨设备通知中枢

#### 场景清单

| # | 场景 | 谁 | 现在怎么做 | 痛点强度 |
|---|------|----|------------|----------|
| B1 | 手机在桌上充电，人在电脑前写代码/办公 | 手机 + PC 同用 | 拿手机看；Phone Link；微信/QQ 桌面版（只覆盖自身） | 高（每天多次） |
| B2 | 手机在另一个房间/包里，等电话/短信 | 居家/外出 | 来回跑，或漏接 | 高 |
| B3 | 开会手机静音，想看紧急通知 | 办公 | 偷偷看手机 | 中 |
| B4 | 登录需要验证码 | 所有人 | 必须拿手机 | 高，但**第三方做不了**（Android 15 敏感通知屏蔽） |
| B5 | 跨品牌：iPhone + Windows 台式机；华为手机 + 非华为电脑 | 混合生态 | 无官方方案；只能拿手机或装多个助手 | 高（唯一差异化空间） |

#### 证据

- 微软官方明确：Android 15 的“敏感通知”会被系统隐藏，包含双因素验证码、一次性密码，Phone Link 也看不到。
- 华为官方明确：协同后只同步短信、微信、QQ、Welink、钉钉、未接来电，其他应用不同步。
- 小米已把“通知同步 + 点击回复”做成生态卖点，甚至支持 iPhone ↔ 小米。
- Phone Link 需要微软账号、机型适配、后台保活，国内体验不稳定；这正是第三方工具的空间，但也是硬仗。

#### 判定

**真需求（高频），但产品位置弱。** 三个减分项：

1. **最高价值场景（验证码）被系统封死**，MVP 只能打 IM/来电/日程，价值打折；
2. **替代品强**：同品牌生态免费、深度集成；跨品牌才有空间，但跨品牌用户是否愿意装第三个 App、开“通知使用权”，未知；
3. **隐私成本高**：通知正文是个人信息，默认全量镜像会被质疑，逐应用授权又会拉低覆盖率。

对一个 pre-launch、单人维护的项目，4 人周投入做“别人已经免费做、且系统限制越来越多”的功能，性价比最低。

#### 修正

**降为 P1，不进 v1.1。** 先做 2 周验证：

- 8 位目标用户访谈：手机通知是否进“前三痛点”；
- 20 人 beta：愿意开“通知使用权”的比例；
- 若门禁通过，MVP 明确**不支持验证码**，主打微信/短信/未接来电/日程，默认逐应用授权、不落盘、可暂停；
- 若门禁不通过，替代方向是“手机屏幕在电脑窗口内查看与控制”（需单独论证），而不是硬做通知。

### 3.3 C｜全设备文件搜索

#### 场景清单

| # | 场景 | 谁 | 现在怎么做 | 痛点强度 |
|---|------|----|------------|----------|
| C1 | 4 台设备，记得文件名不记得在哪台 | 多机用户 | 逐台 Everything/资源管理器；远程桌面；问同事 | 高（每周 1–3 次） |
| C2 | 家里 NAS + 公司电脑 + Mac，跨系统找文件 | NAS/多系统用户 | SMB 映射（常失败）、Everything 网络文件夹、NAS Find、网盘 | 高（替代门槛最高） |
| C3 | 手机上想找电脑里的文件 | 手机 + PC | 微信传给自己、网盘、远程桌面 | 中 |
| C4 | 找上周的合同/发票/截图 | 办公 | 翻下载目录、聊天记录、回收站 | 中 |
| C5 | 接手别人机器/临时项目 | 办公/外包 | 问人、远程、逐个盘翻 | 中 |

#### 证据

- V2EX “Windows 共享文件夹太玄学”：同一网段、防火墙已关，仍有一台电脑访问不了；回复里涉及 SMB 签名、来宾登录、组策略、重装系统。**替代方案对普通用户几乎不可用。**
- NAS Find 作者原话：Windows 用 Everything 定期扫 NAS 很方便，但“日常又用 macOS，搜索 NAS 简直灾难级别”。
- Win 顺把“NAS、别的电脑上的共享文件夹也能一起搜”列为头条能力，说明这是搜索工具的竞争点。
- 商业 LAN 文件搜索工具（10-Strike、LAN Search Pro、Turbo Searcher Network Edition）存在多年，说明“跨机找文件”是可持续的付费/工具品类。

#### 判定

**真需求，三者中最扎实。** 理由：

1. 触发频率中频（每周几次），但**触发时替代成本极高**（SMB 配置、索引部署、跨系统不兼容）；
2. FlyScreen 已有“已配对设备 + 文件通道 + 收件箱”，做搜索是**顺着现有连接加一层检索**，不需要用户再配 SMB；
3. 差异化清楚：**不用共享目录、不用索引服务、不用装第二个工具；命中即可拉到本机**；
4. 可演示、可截图、可写进 README 卖点，对获取第一批用户有帮助。

**但有两点必须承认：**

- 对“只有两台电脑、文件都放 NAS/云盘”的用户，频率会降到每月几次；
- 隐私敏感：搜索别人的文件必须有显式开关、目录白名单、路径校验，不能默认全盘。

#### 修正

保留 P0 主功能，范围收紧：

- 只搜**文件名**（不做全文/OCR）；
- 只搜标准三目录 + 用户显式添加目录；
- 桌面端为被搜索源，手机仅作请求方；
- 未开启搜索的设备在结果页显式提示“未开启”，避免首启空结果；
- 结果命中后走现有 `FileOffer`/收件箱拉取；
- 路径白名单 + realpath 校验，拒绝符号链接逃逸。

## 4. 需求强度对比

| 维度 | A 配对入网 | B 通知中枢 | C 文件搜索 |

| 对 0 用户项目的价值 | 提升首次转化 | 提升日活，但难拉新 | **拉新 + 留存，可演示** |
| 结论 | P0，改定义 | P1，先验证 | **P0，主功能** |

## 5. 收敛后的 v1.1 建议

### 5.1 版本定义

**主题：先“找得到”，再“连得上”。**

| 优先级 | 内容 | 预算 |
|--------|------|------|
| P0 主功能 | C 全设备文件搜索 | 3 人周 |
| P0 配套 | A 零配置连接向导（配对码/二维码 + 手动地址 + 诊断 + 信任中心） | 2 人周 |
| 前置治理 | 工具权限面收窄（`Tool:<id>` 专用通道） | 1 人周 |
| 回归发版 | Win stable 全量回归 + beta | 1 人周 |
| **合计** |  | **6–7 周** |

B 不进 v1.1；2 周验证与 C/A 并行，门禁通过后进 v1.1.1。

### 5.2 与原方案的变化

| 项 | 原方案 | 收敛后 |
|----|--------|--------|
| 范围 | A + B + C，8 周 | C + A，6–7 周 |
| 主功能 | B 通知（旗舰） | C 文件搜索（旗舰） |
| A 的定义 | 配对码/扫码，主打免抄密钥 | 零配置连接向导，主打首次连接成功率 |
| B | P0，4 人周 | P1，2 周验证，不进本版本 |
| 风险 | Android 系统服务 + 隐私合规 | 只剩文件枚举性能与路径安全 |

## 6. 上线前的需求验证计划（2 周）

### 6.1 样本

8 位目标用户，至少覆盖：

- 3 位拥有 ≥3 台电脑；
- 2 位跨 Windows/macOS；
- 2 位 Android + Windows 双持；
- 1 位有 NAS/多存储。

### 6.2 方法

30 分钟访谈 + 3 个任务观察，不让用户“想象”，让他在现有工具上真做：

1. 在 4 台设备中找一份指定文件（记录步骤数、耗时、是否放弃）；
2. 把一台新设备加入现有连接（记录卡点）；
3. 查看手机上的一条通知并在电脑上处理（记录是否愿意授权）。

### 6.3 关键问题（1–5 分）

- 过去一周，你有几次“知道文件在哪台，但找起来很麻烦”？
- 你现在怎么解决？需要几步？失败过吗？
- 如果玄鸟能直接搜已连接设备的三目录，你愿意开启“允许搜索”吗？
- 手机通知上电脑，排在你多设备痛点的第几位？愿意开通知使用权吗？
- 首次连接时，你卡在哪一步？（密钥/发现/防火墙/管理员权限）

### 6.4 门禁

| 功能 | 通过条件 | 不通过则 |
|------|----------|----------|
| C | ≥50% 受访者近一周至少 1 次跨机找文件；且 ≥40% 现有方式需 >2 步/次 | 缩为“最近文件列表”，不做全设备搜索 |
| A | ≥60% 首次连接在无人指导下 5 分钟内完成（改前基线） | 优先做安装器/权限引导，而不是配对码 |
| B | ≥30% 把通知列入前三痛点；且 ≥50% 愿意授权通知访问 | 放弃或改为“手机屏幕窗口化”，单独论证 |

### 6.5 产出

访谈纪要、任务完成率、原话引用、门禁结论；作为 v1.1 PRD 的输入，而不是继续拍脑袋。

## 7. 风险与机会成本

1. **0 用户阶段最大的风险是“为想象的用户做功能”。** B 是最典型的一项：品类有需求，但替代品强、系统封死核心场景。
2. **机会成本要说清：** Mac/Linux 键鼠主路径仍是骨架，Android TV/鸿蒙也未齐。对真实多机用户，补齐主路径的留存价值可能高于 B。新功能预算与平台补齐预算必须分开，不能互相挤占。
3. **A 无法解决管理员权限（UAC）门槛。** 配对码再顺，提权弹窗仍会劝退一部分用户；需要在安装器、首启文案、便携版策略上单独处理。
4. **C 的隐私与路径安全是硬门槛。** 不能为了“搜得全”默认全盘、默认开启；否则一次误搜就会毁掉信任。
5. **B 的合规成本。** 通知正文属个人信息，即使本地处理，也要逐应用授权、可暂停、不落盘、日志脱敏；否则不建议做。

---

## 8. 建议决策

1. **v1.1.0 = C + A（6–7 周）**，B 不进；版本主题改为“找得到、连得上”。
2. **B 用 2 周验证**，与 C/A 并行；门禁通过再排 v1.1.1，不通过则放弃或转向“手机屏幕窗口化”。
3. **A 改定义为“零配置连接向导”**，验收指标从“配对码使用率”改为“首次连接成功率/耗时”。
4. **先做 1 周工具权限面治理**，作为 A/C 的前置护栏。
5. 若资源只够一项，**只做 C**；它是三者中唯一“替代成本高 + 可演示 + 能拉新”的功能。
