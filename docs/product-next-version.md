> **第二轮修订（2026-11-11）：** 本文为初版方案。需求验证结论与收敛后的 v1.1 范围见 [`product-demand-validation.md`](product-demand-validation.md)。核心变化：**C 升为旗舰主功能；A 改定义为“零配置连接向导”；B 降为 P1 验证项，不进 v1.1**；排期由 8 周收敛为 6–7 周。下文 A/B/C 的详细 MVP 仍可作为技术储备，但优先级以验证备忘为准。

> **第三轮评审（2026-11-11）：** 用户对仅剩的 C/A 提出实质质疑——C 的单机搜索已被 Everything/系统搜索覆盖，跨机搜索还要回答“效率”和“会不会卡顿”；A 被认为“基本没有实际使用的价值”。评审结论：**当前候选池已空，v1.1 不应再作为“新功能版本”硬凑内容**。在用户拍板前，§0 的 C+A 范围不视为最终结论；C 的效率/卡顿测算与 A 的价值判断见 §11。

## 0. 结论先行

推荐下一版本定为 **v1.1.0「连接信息」**，交付三项全新能力：

| 编号 | 新功能 | 一句话 | 优先级 |
|------|--------|--------|--------|
| A | 配对入网 2.0 | 新设备输入 6 位配对码，60 秒内完成连接、信任与布局入槽 | P0 |
| B | 跨设备通知中枢 | 手机通知在电脑侧栏出现，可筛选、静音、清除 | P0 |
| C | 全设备文件搜索 | 一个搜索框查 4 台电脑的文件，命中后直接拉到本机 | P0 |

**最终优先级（以验证备忘为准）：** C 为 P0 旗舰主功能 · A 为 P0 配套但改定义为“零配置连接向导” · B 为 P1 验证项，不进 v1.1。

**为什么是这三项：**

1. 三项都复用现有连接、Caps、Bulk 与文件通道，**不碰键鼠注入与投影主路径**，对 Win stable 的回归风险最低。
2. 三项分别补齐「接入层 / 信息层 / 文件层」，把产品从“共享输入输出”推进到“共享信息与资源”，而不是继续堆同类能力。
3. 三项共用同一套身份与信任，后续的手机第二屏、宏键盘、USB 共享都可以复用这套入口。

**前置治理（P0，但不是新功能）：** 当前工具宿主把完整 `ConnectionManager` 暴露给工具，工具可发送任意消息类型、监听全部消息，与 `tools.md` 的“白名单 API”不一致。建议先花约 1 人周收窄为 `Tool:<id>` 专用通道，再上新跨屏能力。

## 1. 现状判断

### 1.1 已交付能力（规划基线）

| 能力域 | 现状 | 备注 |
|--------|------|------|
| 键鼠与布局 | Win stable；Mac/Linux/鸿蒙骨架 | 最多 4 台，1×4 / 2×2，布局同步 |
| 剪贴板 | Win 全格式；Android 文/HTML/图；Mac/Linux 尽力 | 按需拉取，文件半通 |
| 文件 | 直传 / 收件箱 / 穿边拖 | 桌面四端可用 |
| 投影 | 复制 / 扩展 / 声音 / 回控 / 去黑边 / 1 对 1 | 手机可作 Host，不可作 Sink |
| 工具系统 | `.flytool`、工具页、哈希信任、Caps `Tool:<id>`、`ToolSignal`(100) / `ToolData`(101) | 共享设备、取色器已接入 |
| 用户程序 | JS / C# 脚本；Android `Fly.*` / OCR | 本机自动化，不跨机 |
| 多端 UI | WPF / MAUI / Avalonia / 鸿蒙壳 | 七页同构 + 程序 + 工具 |

### 1.2 三个结构性判断

1. **连接能力已经过剩，信息层缺失。**
   4 台设备已经能稳定连上，但几乎所有能力都要求用户“主动操作”：切屏、复制、投屏、传文件。缺少一条“信息自动到达另一台设备”的通道。手机通知是唯一高频、持续产生的信息源，目前完全没有承接。

2. **接入仍是工程师门槛，不是功能缺失。**
   新设备要抄同一串安全密钥、手动添加、再摆布局槽位。对非技术用户，首次成功率低；这是采用率的瓶颈，也是“产品化”与“极客工具”的分水岭。

3. **4 台设备只被当作“屏幕和键鼠”，没有被当作“资源”。**
   屏幕、摄像头、麦克风刚开始共享，但文件资源没有统一入口。用户知道文件在某台电脑，却不知道在哪台；现有直传要求“先知道路径再推送”，与“找文件”是相反的心智。

### 1.3 判定口径：什么算“新功能”

| 计入新功能 | 不计入（既有功能迭代） |
|------------|------------------------|
| 新数据域（通知）、新流程（配对）、新检索面（跨机搜索）、新设备角色（手机作副屏）、新资源类型（USB/打印）、新网络模型（公网） | Mac/Linux 键鼠主路径补齐、鸿蒙电脑、Android TV、投影 H.264、剪贴板 RTF/CSV 补齐、UI 打磨、已有工具 bugfix |

后者继续在 ROADMAP 的 W1–W7 推进，不占本版本的新功能预算。

### 2.2 为什么这些高分项没有排进本版本

| 项 | 后置原因 |
|----|----------|
| 手机第二屏 | 价值最高，但现有 JPEG 约 12fps，做副屏体验不够；应先完成 E2 的编码/延迟优化（H.264、分辨率协商），否则上线即差评。与 v1.2 同批。 |
| USB 共享 | 需要内核级驱动与签名，蓝屏/系统权限风险高，不能与 Win stable 同版本推进。 |
| 公网中继 | 需要打洞/中继/账号体系，会改变“局域网、无云”的产品定位，应单独立项论证。 |
| 浏览器端 | WebRTC 与现有 TCP 协议不兼容，工程量大，收益后置。 |
| 宏键盘 / 电源管理 | 可做且成本低，但价值密度低于前三；作为 v1.1.1 的“小惊喜”更合适。 |
| 1→N 广播 / 批注 | 使用场景集中在会议与课堂，触达窄；且会改动投影的 1 对 1 互斥语义，风险后置。 |

### 2.3 竞品参照（只取结论）

| 能力 | 常见替代 | 对玄鸟的含义 |
|------|----------|--------------|
| 键鼠/剪贴板 | Mouse without Borders、Synergy/Deskflow、罗技 Flow | 已具备，且多端更广；不是本版本重点 |

## 3. v1.1.0 方案

### 3.1 版本主题

**主题：连接信息（Connect the information, not just the devices）。**

一句话目标：让新设备 60 秒入网；让手机的通知出现在电脑上；让 4 台电脑的文件落进一个搜索框。

版本目标（可验收）：

| 指标 | 目标 |
|------|------|
| 首次配对耗时 | ≤ 60 秒（P50） |
| 通知端到端延迟 | ≤ 1 秒（局域网 P50） |
| 10 万文件目录搜索 | ≤ 3 秒（P50） |
| Win stable 回归 | 100% 通过，连接失败率不上升 |

> 三项均为**宿主能力**，不走 `.flytool`：通知监听、文件枚举、连接身份都涉及系统服务或宿主安全边界，工具包无法承载（Android 的 Manifest 服务不能运行时注册）。工具页只提供入口与设置。

### 3.2 功能 A：配对入网 2.0（1.5–2 人周）

**用户故事**

- 作为新用户，我在电脑上看到 6 位配对码，在手机输入后即完成连接，不需要先抄安全密钥、再手动添加、再摆布局。
- 作为老用户，我能在“设备信任”里看到所有配对过的设备，移除丢失设备，阻止陌生设备再次申请。

**MVP（MUST）**

1. 电脑端「安全」页新增「配对入网」卡片：显示 6 位一次性配对码，TTL 120 秒、倒计时、点击刷新。
2. 新设备在发现列表点「配对」→ 输入配对码 → 双向确认设备名与形态 → 交换安全密钥 → 自动加入对端 peer 列表与布局空槽 → 状态“双向已连接”。
3. 配对码 5 次失败 / 5 分钟锁定；只接受同网段 UDP 发现到的设备。
4. 信任中心：已配对设备列表（名称 / 平台 / 形态 / 最后在线 / 移除）；移除后必须重新配对。
5. 旧的手动同密钥流程保留，向后兼容。

**SHOULD**

- 二维码展示（电脑生成、手机扫码）；无相机权限时回退手输。
- 配对时顺带询问「允许对方搜索本机 桌面/文档/下载 的文件名？」，为功能 C 取得显式同意。

**WON'T**

- 账号体系、云同步、跨公网配对、设备证书链、多用户/团队。

**流程**

```text
电脑：安全页 → 显示配对码（120s）
新设备：发现列表 → 配对 → 输入 6 位码
两端：确认设备名/形态 → ECDH 交换 → 校验配对码 → 写入信任列表
电脑：分配布局空槽 → 建立双向连接
失败：码错误/超时 → 明确原因；5 次锁定
```

**技术落点（建议）**

| 层 | 落点 |
|----|------|
| Core | 新增 `Services/Network/PairingService.cs`；`DiscoveryService` 增配对载荷（用 `Kind` 区分，不改现有发现包语义）；`AppSettings` 增 `PairedDevices`；`SecurityKeySyncHelper` 语义不变 |
| 安全 | ECDH（P-256）+ HKDF 派生会话密钥；配对码做二次校验（HMAC）；MUST NOT 明文传输 `SecurityKey` |
| UI | `App.Windows` 安全页卡片 + 配对对话框；`App.Maui` / `App.Desktop` 同构；Android 输入页 |
| 协议 | 不需要新 Cap；新增消息必须可选、旧端忽略 |

**风险与对策**

| 风险 | 对策 |
|------|------|
| 暴力猜码 | 6 位 + TTL + 5 次锁定 + 仅同网段 |
| 中间人 | ECDH + 配对码校验；首次信任依赖“看到同一台机器的码” |
| 旧端不识别 | 仅新端走配对；旧端继续用密钥，互不影响 |
| 布局已满 | 与现有 `RequestLayoutJoin` 的 `full` 拒绝一致，提示明确 |

**验收**

- 新 Win ↔ Android 首次配对 ≤ 60 秒；错误原因可读；5 次错误锁定；移除后不可自动重连。
- 旧 Win ↔ 新 Win 仍可用原密钥连接；Win 回归门禁全过。

### 3.3 功能 B：跨设备通知中枢（3.5–4 人周）

**用户故事**

- 手机在充电，我在电脑上写代码；外卖、家人、验证码通知直接出现在电脑侧栏，不用反复拿手机。
- 开会时手机静音，重要通知仍能在电脑看到；不重要的应用可以静音。

**MVP（MUST）**

1. Android「通知使用权」授权引导（跳转系统设置页）；授权后前台服务常驻（现有 `FOREGROUND_SERVICE` 权限可复用）。
2. 手机 → 电脑镜像：应用名、标题、正文、时间、是否持续/静默；同一 key 去重、按应用折叠；内存最多 20 条，不落盘。
3. 电脑侧栏「通知」页（工具工作区）：按设备分组、按应用筛选、未读计数；托盘提示。
4. 单条操作：复制文本、清除（调用手机 `cancelNotification(key)`）、静音该应用（仅本机）。
5. 全局/单设备暂停；锁屏或敏感应用（可配置名单）默认不镜像正文。
6. 仅局域网、仅已配对设备；日志不写通知正文。

**SHOULD**

- Windows 系统 Toast（未打包应用需要 AUMID/快捷方式；失败回退应用内面板）。
- 按应用聚合摘要（如“微信 3 条”）。
- 免打扰时段。

**WON'T**

- 手机通知直接回复（需 `RemoteInput`，复杂度高）；图片/大文本；PC → 手机反向；历史搜索；云推送。

**技术落点（建议）**

| 层 | 落点 |
|----|------|
| Android | 新增 `Platforms/Android/FlyScreenNotificationListenerService.cs`（`NotificationListenerService`）；Manifest 增加 `BIND_NOTIFICATION_LISTENER_SERVICE` 声明；`POST_NOTIFICATIONS` 已存在；授权跳转 `Settings.ACTION_NOTIFICATION_LISTENER_SETTINGS` |
| Core | 新增 `Services/Notify/NotificationHubService.cs`；载荷 `NotificationEvent`（AppName / Package / Title / Text / PostedAt / Key / Category / Flags） |
| 协议 | 新增宿主消息 `NotificationEvent` / `NotificationAction`（建议 102/103），Control 通道；Caps 增 `NotifyMirror`；不建议复用 `ToolSignal`（该能力不是工具） |
| UI | `App.Windows` 侧栏页 + 托盘；`App.Maui` / `App.Desktop` 同构；Windows Toast 作为 SHOULD |

**风险与对策**

| 风险 | 对策 |
|------|------|
| 隐私 | 默认只显示用户勾选的应用；敏感名单；不落盘；随时暂停；授权页明确“仅局域网、不上传” |
| 系统限制 | Android 各厂商可能杀服务：前台服务 + 引导关闭电池优化 + 断线重连；Windows Toast 不可用则面板兜底 |
| 噪音 | 去重、聚合、静音、免打扰时段 |
| 合规 | 通知内容属个人信息：最小必要、本地处理、显式同意、可关闭、可清除；不新增云端 |

**验收**

- Android → Win 延迟 P50 ≤ 1 秒；连续 100 条不丢不崩；去重正确；清除后手机通知同步消失；敏感应用不显示正文；日志无正文；Win 回归全过。

### 3.4 功能 C：全设备文件搜索（2.5–3 人周）

**用户故事**

- 我知道那份合同在 4 台电脑的某一台，但不想逐台找。在搜索框输入“合同”，直接看到来自哪台、路径、大小，点一下拉到本机。

**MVP（MUST）**

1. 新增侧栏「文件」页（或工具工作区「全设备文件」）：搜索框 + 设备筛选 + 结果列表（按设备分组）。
2. 查询条件：文件名包含、扩展名、修改时间（近 7/30/365 天）、每台最多 50 条；总超时 3 秒。
3. 搜索范围：对端标准三目录（桌面/文档/下载）+ 用户显式添加的目录；默认不含全盘、不含隐藏/系统目录。
4. 结果操作：拉到本机（走现有 `FileOffer`/收件箱）、复制路径、在本机打开（仅本机结果）、发送到另一台（SHOULD）。
5. 对端必须显式开启「允许其他设备搜索本机文件」；未开启设备在结果页显示“未开启搜索”并给一键开启入口。
6. 仅已配对/已连接设备；查询只接受“预先配置的根目录”，MUST NOT 接受请求方传入任意路径（防远程目录遍历）。
7. 大小写不敏感；中文文件名正常；长路径/特殊字符不崩。

**SHOULD**

- 本地缓存（路径 + 大小 + 修改时间）5 分钟，重连失效。
- 手机作为请求方（搜索电脑，结果拉到手机收件箱）；手机不作被搜索源（Scoped Storage 复杂）。

**WON'T**

- 全文内容搜索、OCR、图片内容检索；跨公网；手机文件源；常驻索引服务。

**技术落点（建议）**

| 层 | 落点 |
|----|------|
| Core | 新增 `Services/Files/FileSearchService.cs`；新增 `FileSearchQuery` / `FileSearchReply`（建议 104/105，Control 通道，小载荷、分页） |
| 复用 | `RemoteFoldersQuery/Reply`（57/58）取标准目录；`FileTransferService` 做拉取 |
| 平台 | `FlyScreen.Windows` 文件枚举（长路径、权限跳过）；Mac/Linux 同构；Android 仅请求方 |
| Caps | 新增 `FileSearch`；旧端无此 Cap → 不参与搜索，UI 说明“对端版本过低” |
| 安全 | 根目录白名单 + 结果路径校验必须位于根目录内；解析真实路径后再校验，拒绝符号链接逃逸 |

**风险与对策**

| 风险 | 对策 |
|------|------|
| 性能 | 深度/数量/超时限制 + 5 分钟缓存；先只搜三目录；大目录提示“范围过大，请缩小” |
| 隐私 | 默认关闭 + 显式开启 + 可视化“哪些目录被共享搜索”；配对时取得同意 |
| 权限 | 无权限目录跳过并计数，不阻塞整体 |
| 路径安全 | 白名单根目录 + realpath 校验；拒绝 `..`、符号链接、UNC 越界 |

**验收**

- 10 万文件目录 P50 ≤ 3 秒（SSD、单目录树）；文件名子串命中准确率 100%；拉取成功率 ≥ 99%；路径逃逸测试拒绝；Win 回归全过。

## 7. 风险与前置治理

1. **工具权限面（P0 前置）。**
   `ToolHostServices` 通过 `GetService<ConnectionManager>()` 把完整连接管理器交给工具；工具因此可发送任意 `MessageType`、监听全部消息（`MessageReceived`）。这与 `tools.md` 的“白名单 API、MUST NOT 接触注入”不一致。建议新增 `IToolPeerChannel`：只允许发送本 `ToolId` 的 `ToolSignal`、只接收本 `ToolId` 的信封；约 1 人周。这是上新跨屏工具前的护栏，不算新功能。

2. **Android 系统服务归属。**
   通知监听、无障碍、MediaProjection 必须在宿主 Manifest 内声明，`.flytool` 无法运行时注册。因此 B 必须是宿主能力；工具页只做入口。

3. **协议兼容。**
   新消息全部可选、旧端忽略；新增 Caps 只做门控；不升 `ProtocolVersion`；发版按 `protocol.md` 的三组交叉测试执行。

4. **Win 零回退。**
   A/B/C 均不改输入注入与投影主路径；回归按 `runbooks/regression-windows.md` 全跑，任一失败则不发版。

5. **单开发者带宽。**
   三项并行会拖长。建议串行 A → B → C，B 先出内测；每周可演示增量。

6. **隐私与合规。**
   通知与文件名属个人信息：本地处理、最小必要、显式同意、可关闭、可清除；不新增云端与账号。

## 11. 第三轮评审（2026-11-11）：C/A 价值复核

### 11.1 C 全设备文件搜索：必要性与性能

用户的问题：Everything 与系统搜索已能搜单机，跨机搜索是否必要？效率和卡顿如何？

**必要性**：只有当“不知道文件在哪台机器”且“切机 + 搜索 + 拉取”超过 3 步时，跨机搜索才有价值。若用户按机器分区存放文件，或文件都在 NAS/云盘，跨机搜索只是“顺手”，不是“刚需”。它不是 P0。

**三条实现路径的成本对比**：

| 路径 | 查询效率 | 卡顿风险 | 覆盖 | 成本 |
|------|----------|----------|------|------|
| 查各机系统索引（Windows Search / Spotlight / locate） | 快，单机几十到几百 ms | 低（索引是系统已有） | 不一致：Win Search 默认只索引部分目录；Mac 隐私设置会排除；Linux locate 可能过期；Android/鸿蒙没有全局文件名索引 | 中：3–4 套平台实现 + 权限/覆盖差异处理 |
| 自建索引（爬白名单目录 + USN/FSEvents/inotify 增量） | 快，ms 级 | **有**：首次全量扫描 CPU/磁盘/内存尖峰；常驻 watcher；笔记本电池/发热；4 台各建一套 | 一致，可搜全部白名单目录 | 高：6–8 周量级，且长期维护权限、外接盘、Unicode、符号链接 |
| 查询时实时遍历（限深度/结果/3s 超时） | 慢，单机 1–10s；4 台并行更慢；超时即不全 | **有**：每次查询打到远端磁盘，远端机器可能瞬时不响应 | 只覆盖遍历到的目录 | 低：2–3 周，但体验不可控 |

**结论**：要“快且全”，就必须有索引；有索引就有后台 CPU/磁盘/内存成本；不要索引，就“慢且不全”。不存在既快又全又不占资源的方案。用户对卡顿的担心成立。C 若保留，只能缩为“只搜显式共享的白名单文件夹、默认关闭、逐目录授权、结果上限 50、超时 3s、不搜正文”，并且接受“搜不全”的预期管理；这仍不是 3 周的轻功能。

### 11.2 A 零配置连接向导：实际价值

A 是一次性开通功能，价值 = 新用户激活率 × 新用户数。项目处于 pre-launch，没有外部新用户样本——但这不是 A 没价值的理由。A 对你价值为 0 的真正原因是：你自己会配对，向导不解决你的任何一次操作；对未来的非技术用户它才有价值，而那是产品化阶段的事，不是现在。

真正卡首次连接的是环境问题（跨网段、防火墙、管理员权限、发现不到），向导能缓解但不能消除；对技术型目标用户，一份排障文档 + 手动地址兜底可能就够了。A 只有在“开始面向非技术用户规模化”时才有意义，而那是另一个产品策略，需要安装器、权限、支持、文档一起做，不是一个 2 周的向导能解决的。

**结论**：A 在当前阶段没有实际使用价值，撤下；若要保留最小投入，只做“连接诊断面板”（显示发现的 peer、网段、端口、单向连接），3–5 天，不做向导。

### 11.3 候选池为空之后的三个选择

1. **不做新功能版本**：v1.1 改为“核心完成版”——Mac/Linux 键鼠主路径、连接稳定性、H.264/E2、Android/鸿蒙稳定性。它不是新功能，但比任何剩余候选都更能带来真实用户。
2. **换定位/换人群**：先花 2 周找一个现有工具覆盖不了的细分（例如 Windows + Android + 鸿蒙、局域网、无账号、开源的组合），用证据决定，而不是继续在 12 项里挑。
3. **暂停版本规划，先记自己的痛点**：pre-launch 没有外部需求信号；先连续两周记录你自己跨设备时的摩擦（哪次找文件、哪次配对、哪次传文件卡住），两周后只有反复出现的痛点才值得立项。

**PM 判断**：连续否掉 D/F/E/C/A，这些否决都来自你对自身使用场景的判断，不是外部 Star 数；问题不在候选池，而在产品还没有一个“你非用它不可”的场景。继续找功能，大概率得到更多“这个也能被替代”的答案；下一步应先把“谁非用它不可”定义清楚。
